OpenTelemetry em uma página

Um padrão aberto e neutro para gerar, coletar e enviar telemetria. Não é um banco de dados nem uma tela: ele entrega os dados para a ferramenta que você escolher.

NA DEMO o que já usamos na checkout-api

O problema que ele resolve

Antes

Cada ferramenta tinha seu agente, sua biblioteca e seu formato. Trocar de fornecedor significava instrumentar o código de novo.

App→agente A→ferramenta A+agente B→ferramenta B

Com OpenTelemetry

O código é instrumentado uma vez, com uma API padrão. O destino vira configuração: muda-se o exportador, não a aplicação.

App + OTel→OTLP→qualquer backend compatível

O que mantém tudo conectado

Propagação de contexto

O trace_id passa de um serviço para o outro em um cabeçalho HTTP padrão (W3C). É o que une spans de serviços diferentes em um único trace.

traceparent: 00-4bf92f35…4736-00f067aa0ba902b7-01

Convenções semânticas

Nomes padronizados para os atributos. Como todos usam os mesmos nomes, qualquer ferramenta entende os dados sem configuração.

http.request.method   http.route
http.response.status_code   service.name

Novas frentes

IA generativa: convenções gen_ai.* para modelo, tokens e chamadas de ferramentas (em desenvolvimento).
eBPF (OBI): instrumentação a partir do kernel, sem alterar o código da aplicação.

Três confusões comuns

"OpenTelemetry substitui o Jaeger e o Prometheus."Não. Ele gera e transporta os dados; essas ferramentas guardam e exibem.
"Com auto-instrumentação, não preciso mexer no código."Ela cobre o técnico (HTTP, banco). O que é do negócio, como process_order, só você sabe marcar.
"Adotar OTel é trocar tudo de uma vez."Não. Na demo, traces já são OTel, enquanto métricas e logs seguem com as bibliotecas anteriores.
