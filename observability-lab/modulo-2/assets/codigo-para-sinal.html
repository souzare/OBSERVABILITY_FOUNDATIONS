Passe o mouse (ou clique) nos trechos sublinhados: o que está no código acende no resultado

Nenhum log aparece sozinho. Cada campo que vemos no terminal foi escolhido e escrito por alguém no código. Se o campo não está no código, ele não existe na hora do incidente.

No terminal a linha vem compacta; aqui está quebrada para facilitar a leitura.
Repare no trace_id: ele vem do span criado pelo OpenTelemetry. É essa linha de código que permite sair de um log de erro e cair direto no trace no Jaeger.

A aplicação não envia métricas: ela conta em memória e publica os totais em /metrics. O Prometheus passa a cada 5 segundos, lê a página e guarda o histórico.

Cada combinação de labels vira uma série. Por isso o label endpoint usa a rota (/orders/:id) e não o caminho real: um valor por pedido criaria milhares de séries.
Só é possível filtrar e agrupar pelos labels que foram declarados no passo 1.

Um trace é um conjunto de spans. Cada span é um trecho de código que alguém marcou com "começa aqui" e "termina aqui". A barra no Jaeger é exatamente o tempo entre essas duas linhas.

O que escrevemos em app.js

1Dizer quem somos e para onde enviar app.js:30-43
const sdk = new NodeSDK({
  resource: resourceFromAttributes({
    [[servico|'service.name': SERVICE_NAME]],
    'service.version': SERVICE_VERSION,

Sem o passo 4 o trace teria uma única barra: saberíamos que a requisição demorou 460 ms, mas não onde. Quanto mais trechos marcamos, mais detalhada fica a história.
O Jaeger só permite buscar por customer_id porque o passo 3 gravou esse atributo.
